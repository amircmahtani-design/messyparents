# What to upload to GitHub

**32 files to upload. 4 to delete.** (33 in the zip — one is this note.) Everything else you saw in the full zip is
generated by Netlify on deploy and does not belong in the repo — your repo never
contained it before this work and should not start now.

Drag-and-drop through the GitHub web UI, exactly as you always do. Keep the
folder structure: dropping a folder onto GitHub preserves the paths inside it,
so you can drop `assets`, `scripts`, `tests` and `data` as folders rather than
placing each file by hand.

## 3. What you must NOT upload

The full zip contained about 630 files that are **build output**. Netlify writes
all of them on every deploy, from Firestore:

```
guides/           a real HTML page per guide          31 dirs today, 500 later
topics/           the five topic landing pages
ages/             the seven age landing pages
sitemap.xml
llms.txt
_redirects
seo-audit.html
test-results/
data/guide-index.json
data/guide-search.json
data/site-settings.json
```

Committing these would mean uploading hundreds of files by hand, and they would
go stale the moment you edited a guide. The new `.gitignore` lists them all, so
once it is in place Git will simply ignore them.

**If any of them are already in your repo, delete them from GitHub once.** The
live site will not change — Netlify regenerates them on the next deploy.

## 4. After the deploy

1. **Paste your Netlify build hook into Studio** → Site → Search & AI, if you
   have not already. This matters more than it used to: the public site is
   static now, so the rebuild is what publishes. Once it is set, Studio fires it
   automatically 90 seconds after your last save.
2. Open a guide, then **View Source**. You should see two `<script src>` tags,
   not five, and no `guides.js`.
3. Run PageSpeed on mobile for `/`, `/guides.html` and a guide page.
   The typography, the CSS and every image are byte-identical to what you had,
   so nothing should look different — only faster.
4. Optionally set **`MPC_REQUIRE_FIRESTORE=1`** in Netlify's environment
   variables. If a build ever cannot reach Firestore, it will then keep the
   previous deploy live instead of publishing a site missing your newest guides.

## A note on the file count you saw

Two things inflated it, and one of them was my fault:

- **~630 files are Netlify's build output**, as above. Normal, and not yours to
  upload.
- **469 of them were junk from my scale test** — synthetic guides like
  `guides/wont-nap-v497/` that the test creates to measure performance at 500
  guides. The harness restored your data but the build had no way to clear the
  leftover pages. Fixed twice over: the residue is gone, and `scripts/build.js`
  now removes stale generated pages on every run. That also fixes a real problem
  you would have hit eventually — renaming a slug in Studio used to leave the
  old page behind as an indexable duplicate.

## Visual identity

Nothing about how the site looks was changed. Verified against your original,
file by file:

```
assets/css/tokens.css     byte-identical
assets/css/style.css      byte-identical
assets/css/guide.css      byte-identical
every image               byte-identical
the Google Fonts request  byte-identical
```

The only differences in the page markup are two things a reader cannot see:

1. The `preconnect` to `firebasestorage.googleapis.com` is gone — a network
   hint to a host no page ever contacted.
2. The hero `<img>` now has its `src` written in, plus `class="ready"`. Same
   image, same `width`/`height`, same alt text. It used to arrive with no `src`
   at all and was held invisible by CSS until JavaScript filled it in; now it is
   simply there. That is the biggest single speed win here, and it makes the
   page look *more* like itself, sooner.

An earlier draft trimmed Baloo 2 from three weights to one. That has been
reverted — see the note in `SEO_AI_ARCHITECTURE.md` under Performance. There is
now a test pinning the font request exactly as it shipped, so it cannot drift.
